# DevDistrict 3.0 — публикация игры

Эта версия размещает страницу и API на одном Node.js-сервере. Браузер обращается к /supabase на адресе игры; сервер обращается к существующему Supabase через HTTPS + HTTP/1.1. Существующие аккаунты, SQL и прогресс в базе сохраняются. Браузер больше не устанавливает прямые HTTP/2/WebSocket-соединения с *.supabase.co.

Сеть пользователя всё ещё может блокировать новый хостинг. Гарантировать доступ из любой страны и сети невозможно. Этот проект меняет маршрут, связанный с наблюдавшимися ERR_CONNECTION_RESET и ERR_HTTP2_PING_FAILED, но фактическую доступность нужно проверить после публикации.

## 1. Создать репозиторий

1. Распакуйте архив.
2. Откройте https://github.com/new, создайте репозиторий **DevDistrict-Server**, выберите Public и добавьте README.
3. Нажмите Add file → Upload files. Перетащите ВСЁ СОДЕРЖИМОЕ папки DevDistrict-3 в корень репозитория. Разрешите замену README.md. Нажмите Commit changes.
4. Убедитесь, что package.json, package-lock.json, server.mjs, render.yaml, public-config.js и папка dist лежат в корне. Не загружайте ZIP вместо файлов. node_modules в архиве нет и загружать его не нужно.

## 2. Опубликовать на Render

1. Откройте https://dashboard.render.com/ и войдите/зарегистрируйтесь.
2. New → Web Service. Подключите GitHub и выберите DevDistrict-Server.
3. Заполните:
   - Language / Runtime: Node.
   - Branch: main.
   - Region: Frankfurt (для аудитории в Европе; при другой аудитории выбирайте ближайший доступный регион).
   - Root Directory: оставьте пустым.
   - Build Command: `npm ci --include=dev && npm run build`
   - Start Command: `npm start`
   - Instance Type: Free для бесплатной проверки.
4. Добавьте переменную окружения NODE_VERSION со значением 22, если интерфейс предлагает Environment Variables. В render.yaml она уже задана для публикации через Blueprint.
5. Нажмите Deploy Web Service и дождитесь состояния Live. В логах должна появиться строка `DevDistrict 3 ready on port ...`.
6. Скопируйте публичный HTTPS-адрес сервиса, который показывает Render, и откройте игру по НЕМУ. Это новый адрес для игроков.

Альтернативно: New → Blueprint → этот репозиторий → подтвердить ресурсы из render.yaml. Он содержит все указанные команды. Не создавайте одновременно два сервиса.

ВАЖНО: GitHub Pages не выполняет Node.js. Эту сборку нельзя публиковать как обычные index.html + assets на Pages. GitHub здесь хранит проект, Render запускает его сервер. Старый сайт Pages не изменяется при загрузке нового репозитория.

Бесплатный Render засыпает после 15 минут без входящих запросов; первое открытие после простоя может занять около минуты. Во время активной игры идут запросы. Для постоянного сервиса без такого ожидания нужен тариф, который не засыпает; проверьте текущую стоимость перед выбором. Код проекта тот же. Не используйте искусственные запросы для обхода ограничений бесплатного тарифа.

## 3. Supabase — только адрес возврата

1. Откройте существующий проект Supabase → Authentication → URL Configuration.
2. В Site URL укажите точный новый адрес Render с `/` на конце.
3. Добавьте такой же адрес в Redirect URLs и сохраните.
4. Если пользователь подтверждает регистрацию через письмо, новые письма должны возвращать его на новый сайт. Ранее высланные ссылки могут содержать старый адрес.

URL проекта и его ПУБЛИЧНЫЙ ключ уже включены в public-config.js. Не вставляйте service_role, sb_secret или пароль базы. SQL запускать, таблицы удалять и базу пересоздавать НЕ НУЖНО.

Опционально владелец другого проекта может задать SUPABASE_URL и SUPABASE_PUBLIC_KEY на сервере. Эта сборка ожидает существующую схему DevDistrict и sb_publishable_ ключ.

## 4. Проверить результат

1. Откройте новый сайт на своём компьютере и у тестера.
2. Войдите существующим аккаунтом по почте и паролю. На новом домене потребуется войти заново.
3. Гостевые сессии привязаны к прежнему адресу и браузеру: гостевой прогресс автоматически на новый домен не переносится. Если старый гость важен, сохраните доступ к старому сайту; не очищайте его данные браузера.
4. Проверьте движение и видимость второго игрока. Обновления других игроков приходят примерно раз в 1.5 секунды плюс время запроса, а при сбоях — реже.
5. Откройте ссылку «Проверка соединения» внизу страницы. Нажмите «Проверить». Она показывает время полного запроса через сервер и отдельно время доступа сервера к сервису авторизации базы. Это не замер выполнения игровых SQL-функций.
6. В F12 → Сеть игровые запросы должны идти на адрес нового сайта с путём /supabase/rest/v1/...; прямых запросов браузера к *.supabase.co быть не должно.
7. Если видите старую версию 2.2.3 — открыт старый адрес. В новой версии вверху написано DEV DISTRICT 3.0.

Если ошибка осталась, сохраните результат «Проверки соединения» и статус неудачного запроса. HTTP 502/504 нового сервера означает, что он не получил полный ответ базы; сброс без HTTP-статуса означает проблему между браузером и новым сервером. Страница /healthz проверяет только запуск сервера, а не базу.

## 5. Локальный запуск на Windows

Для проверки на своём компьютере нужен Node.js 22 или новее. Распакуйте архив и запустите START-WINDOWS.cmd. Он поддерживает папку на сетевом диске через pushd. Откройте http://localhost:3000. Папка dist уже собрана, npm install для этого запуска не нужен. Окно сервера оставьте открытым.

Для проверки из терминала: `node server.mjs`.
После изменения исходников: `npm ci --include=dev`, затем `npm run build` и `npm start`.
Локальный запуск не создаёт общедоступную интернет-ссылку. Для постоянной ссылки используйте публикацию выше.

## Что исправлено

- Все обращения браузера к базе проходят через тот же домен, что и игра.
- Исходящие запросы сервера используют HTTP/1.1 и обычную проверку TLS-сертификата.
- Ответ читается целиком до отправки клиенту: частично оборванный HTTP 200 превращается в понятную 502.
- Таймаут сервера ограничен 10 секундами; клиент читает полный ответ в пределах 15 секунд.
- Сервер не повторяет изменяющие запросы. Клиент повторяет только GET один раз; списания и награды автоматически не дублируются.
- Фоновое присутствие не блокирует кнопки и движение.
- Синхронизация игроков работает без прямого WebSocket к Supabase, с увеличением интервала при ошибках.
- Показано время последнего успешного игрового запроса, а не сглаженное среднее.
- Ошибка рейтинга из-за отсутствующего id обработана.
- Proxy разрешает только нужные маршруты, передаёт личный Bearer-токен пользователя и не использует секретный административный ключ. RLS и серверные игровые проверки продолжают действовать.

## Проверки и ограничения

`npm test` — тесты HTTP/1.1, TLS, двух SDK-клиентов, входа, движения, чтения игроков, выхода, обрыва ответа, таймаута, ограничения маршрутов и отсутствия повторных POST. Тестовая база в интеграционном тесте имитируется; это не проверка производительности живого Supabase. tests/fixtures содержит только локальные тестовые сертификат и ключ, которые сервер в обычном запуске не использует.

`npm run build` проверяет сборку, синтаксис, целостность файлов и отсутствие прямого URL Supabase в клиентском JS.

Живой сервер не опубликован автоматически: нужно пройти шаг 2 в своём аккаунте Render. Из среды подготовки живой Supabase не удалось проверить из-за DNS EAI_AGAIN. Гарантий конкретного ping нет. Текущий игровой мир по существующим правилам базы ограничен 10 одновременно активными игроками.
